1. Executive Summary & Business Model

The platform is an online learning business for secondary and senior-secondary students (Classes 9–12 at launch), sold through a B2B2C channel: the company signs commission contracts with schools and colleges (“Institutes”), and those Institutes enroll their students onto the platform.

1.1 How the business works

  • The company produces and curates video lessons, PDF study material, and test series for every subject of Classes 9, 10, 11 and 12.
  • Teaching and grading are delivered by the company’s own central pool of teachers, serving every Institute. Institutes do not supply teaching staff.
  • Each Institute signs a written, e-signed contract committing to a minimum number of students over a defined period, in exchange for a commission that is either a percentage of student fees or a fixed amount per student.
  • When a student pays, the platform automatically splits and settles the Institute’s commission through Razorpay Route, and tracks the Institute’s progress against its committed student count.
  • Students can also arrive directly from the marketing website; these are attributed to a system “Direct” tenant so a single commission code-path applies everywhere.

1.3 MVP success criteria

  • An Institute can be onboarded, sign a contract, and have its students enrolled and paying within one working day.
  • A student can watch lessons, download material, take an MCQ test, receive AI-generated weak-topic analysis, and be served an adaptive retest — end to end — on web and mobile.
  • A subjective test can be taken under proctoring, graded by a teacher, and returned with analysis.
  • Every rupee collected is reconciled: platform revenue, tax, coupon cost, and Institute commission settled and reportable.
  • Super Admin can impersonate any user for support, with a full audit trail.

2. Goals, Non-Goals & MVP Boundary

2.1 Goals

  • One backend, four clients, clean REST API, multi-tenant by Institute.
  • Complete contract-to-commission lifecycle with automated settlement.
  • Complete learn-to-assess-to-improve loop with AI analysis and adaptive retests.
  • Anti-piracy content delivery (signed URLs, per-user watermarking, screen-capture protection on mobile).
  • Role-based access with impersonation and full audit logging.
  • Compliant handling of minors’ data and proctoring recordings (India DPDP Act).

2.2 Non-Goals for v1

  • Live / synchronous online classes (Zoom / Meet integration) — planned v2.
  • Regional-language content and UI — English only at launch, i18n-ready structure.
  • SMS / WhatsApp notifications — abstraction in place, provider added later.
  • Public marketplace / self-serve Institute signup without a signed contract.
  • Advanced gamification, social feed, peer messaging.
  • Offline-first web app; only the mobile app supports offline content.

4.1 Architectural principles

  • Modular monolith NestJS API (modules: auth, tenants, institutes, contracts, crm, marketing, students, catalog, media, assessments, ai, proctoring, payments, commission, notifications, reporting, admin). Split to services only if load demands it.
  • API-first & versioned (/api/v1). All four clients consume the same contract; the mobile app must never require a bespoke endpoint shape.
  • Multi-tenant by instituteId (with a reserved DIRECT tenant). Tenant scoping applied in a global query guard; cross-tenant access is a test-covered invariant.
  • Async by default for anything slow or external — queued via BullMQ with retry/backoff and dead-letter handling.
  • Stateless API nodes; sessions/refresh tokens and rate-limit counters in Redis; horizontal scale behind a load balancer.
  • Signed, expiring URLs for every piece of protected media (video playback tokens, PDF links, proctoring uploads).
  • Idempotent webhooks (Razorpay, Bunny, e-sign) keyed by event id; all webhook signatures verified.

6. Functional Requirements

Each sub-section lists requirements with stable IDs and, for flagship features, acceptance criteria. Unless tagged otherwise every requirement is P1 — MVP.

6.1 Identity, Authentication & RBAC

  • FR-AUTH-01 Email + password registration and login; passwords hashed with bcrypt/argon2; email verification required before first paid action.
  • FR-AUTH-02 OTP login (email) for students/parents; optional biometric unlock on mobile after first login.
  • FR-AUTH-03 JWT access token (short-lived) + rotating refresh token stored server-side (Redis); refresh revocation on logout / password change.
  • FR-AUTH-04 Forgot-password with time-boxed single-use token.
  • FR-AUTH-05 TOTP 2FA: mandatory for Super Admin, Ops, Sales, Marketing, Teacher; optional for Institute Admin.
  • FR-AUTH-06 Device / session limit for Student accounts (default 2 active devices); registering a 3rd forces logout of the oldest; visible session list.
  • FR-AUTH-07 Impersonation: Super Admin starts “View as <user>”; a persistent banner shows on every screen with an Exit impersonation action; impersonated session cannot change passwords, 2FA, or payout settings.
  • FR-AUTH-08 Parent–student linking via invite code or Institute-provided mapping; a Parent may link multiple students; a student may have one primary Parent.
  • FR-AUTH-09 Global audit log with filter/search/export; entries immutable; retained per §11 retention policy.
  • FR-AUTH-10 Account lockout / exponential backoff after repeated failed logins; suspicious-login email.
Acceptance — Impersonation Given a Super Admin impersonating a Student, when they open any page or call any API, then responses reflect the Student’s permissions and data, the audit log records both the real admin id and the target id, and ending impersonation returns the admin to their own session without re-login.

6.2 Institute & Partner Management

  • FR-INST-01 Create Institute: legal name, display name, type (school/college/coaching), address, city/state, GSTIN, PAN, primary + billing contacts, logo.
  • FR-INST-02 KYC document upload (registration certificate, PAN, GST, cancelled cheque / bank proof) with per-document verification status.
  • FR-INST-03 Institute lifecycle: PROSPECT → ONBOARDING → ACTIVE → SUSPENDED → CHURNED; state changes are audited and can gate student enrollment.
  • FR-INST-04 Unique Institute referral code auto-generated; used at student signup for commission attribution; regeneratable with history.
  • FR-INST-05 Razorpay Route Linked Account creation & KYC status tracking per Institute; commission settlement blocked until active.
  • FR-INST-06 Commitment tracking: committed student count vs enrolled vs paid; progress %, projected shortfall, and alerts at configurable thresholds (e.g. 60 days to term-end and <70% of commitment).
  • FR-INST-07 Commission ledger per Institute: accrued, pending settlement, settled, adjustments, disputes, running balance.
  • FR-INST-08 Institute data export (own students + performance) as CSV/Excel.
  • FR-INST-09 Notes, tasks, and file attachments on the Institute record (shared with Sales CRM §6.4).

6.3 Contract Handling & E-Signature

  • FR-CTR-01 Contract created from a versioned template or by uploading a prepared PDF.
  • FR-CTR-02 Structured terms captured alongside the document:
    • Commission model: PERCENTAGE (of net student fee) or FIXED (₹ per enrolled/paid student).
    • Commission rate / amount; optional slabs (e.g. 10% up to 200 students, 12% beyond).
    • Minimum student commitment (count) and commitment period (start & end dates).
    • Settlement cycle: PER_TRANSACTION or WEEKLY or MONTHLY.
    • Commission basis: gross vs net of coupon (default net); refund clawback rule.
    • Renewal terms, notice period, termination clause.
  • FR-CTR-03 E-signature via integrated vendor: send for signature, track signer status, receive signed PDF + tamper-proof audit trail via webhook.
  • FR-CTR-04 Contract states: DRAFT → SENT → SIGNED → ACTIVE → EXPIRING → EXPIRED / RENEWED / TERMINATED.
  • FR-CTR-05 Only an ACTIVE contract enables commission calculation; term changes require a new version or addendum (old versions retained & viewable).
  • FR-CTR-06 Automatic expiry reminders to Sales + Super Admin at 60/30/7 days.
  • FR-CTR-07 Contract approval gate: Super Admin countersign / approve before ACTIVE.
Acceptance — Contract to commission Given an ACTIVE percentage contract at 12% net, when a mapped student pays ₹10,000 with a ₹1,000 coupon, then commission accrued = 12% × ₹9,000 = ₹1,080, a Route transfer of ₹1,080 is scheduled per the settlement cycle, the Institute ledger updates, and the student counts toward commitment on successful payment capture.

6.6 Student Management

  • FR-STU-01 Enrollment paths: (a) Institute bulk import, (b) Institute/campaign referral link, (c) direct website signup (→ DIRECT tenant).
  • FR-STU-02 Student profile: name, DOB, contact, board, class (6–12), stream, subjects, batch, Institute mapping, parent link, status, acquisition metadata.
  • FR-STU-03 Bulk CSV import by Institute Admin: template download, row validation, dedupe, dry-run preview, error report, auto credential generation, welcome email with app links.
  • FR-STU-04 Status: INVITED → ACTIVE → SUSPENDED → EXPIRED → REFUNDED; access derived from status + purchased plan + class.
  • FR-STU-05 Content/test access is computed: a student sees only their class & subjects, plus free/sample items, plus anything their plan grants.
  • FR-STU-06 Attribution & re-attribution policy: first valid Institute code wins for the current term; later code changes are logged and take effect from the next billing cycle; disputes flagged for Ops.
  • FR-STU-07 Parent consent gate for students under 18: signup incomplete until Parent approves (see §11).

6.7 Course & Content Management (LMS admin)

  • FR-CNT-01 Taxonomy: Board → Class → Subject → Chapter → Topic → Lesson. Every content item and question is tagged to a Topic (drives AI analysis & test blueprints).
  • FR-CNT-02 Content types: video (Bunny), PDF/notes/resource (S3), external link. Each item: title, description, topic tags, difficulty, free/paid flag, order, status.
  • FR-CNT-03 Workflow: DRAFT → IN_REVIEW → PUBLISHED; schedule publish/unpublish; content versioning with rollback.
  • FR-CNT-04 Bulk content tooling: batch upload of videos (with metadata CSV), batch PDF upload, batch topic re-tagging. Treated as a first-class workstream given catalogue volume (all subjects × 4 classes).
  • FR-CNT-05 Content search & filters for admins; broken-link / missing-media report.
  • FR-CNT-06 Per-student progress capture API: video position & % watched, lesson complete, chapter complete, time-on-content; powers dashboards & AI.
  • FR-CNT-07 Student-side content features (web + mobile): resume playback, bookmarks, personal notes, rate/report a lesson.

6.8 Video Delivery (Bunny.net)

  • FR-VID-01 Server-side upload / TUS pipeline to Bunny; transcode to adaptive HLS renditions; poster/thumbnail generation.
  • FR-VID-02 Playback only via token-signed, short-expiry URLs issued per student per session; referrer / allowed-origin lock; no raw CDN URL exposed to the client.
  • FR-VID-03 Dynamic watermark overlaying student id / email / phone, position rotating periodically (anti screen-record).
  • FR-VID-04 Player features: speed control, quality selector, resume, chapters, captions/subtitles upload, keyboard shortcuts (web).
  • FR-VID-05 Mobile: DRM-capable player, screenshot / screen-record blocking (Android FLAG_SECURE, iOS capture detection), screen-mirroring / external-display block during playback.
  • FR-VID-06 P1 Offline download (mobile): encrypted local store, per-title download, device-bound, expiry (e.g. 30 days / re-validate every 7), max concurrent downloads, admin toggle per content item to allow/deny offline.
  • FR-VID-07 Bunny webhook handling for encode-complete / failure; ret/alert on failure.
  • FR-VID-08 Playback analytics event stream (start, progress pings, complete, errors) stored for reporting & AI.

6.9 Study Material / PDF

  • FR-PDF-01 Upload PDFs/resources to object storage; served only via signed expiring links.
  • FR-PDF-02 In-app / in-browser PDF viewer with per-student watermark (name, id, timestamp) stamped on view.
  • FR-PDF-03 Per-item flags: allow/deny download, allow/deny print.
  • FR-PDF-04 Mobile offline access for permitted PDFs uses the same encrypted store & expiry as video (FR-VID-06).

6.10 Assessment & Test Engine

  • FR-ASM-01 Question bank item types: MCQ single-correct, MCQ multiple-correct, numerical/integer, subjective/descriptive. Fields: stem (rich text + images + LaTeX), options, correct answer(s), marks, negative marks, expected time, difficulty, solution/explanation, board/class/subject/chapter/topic tags, status.
  • FR-ASM-02 Bulk question import (Excel/CSV/Word template) with image handling & validation report.
  • FR-ASM-03 Test types: topic-wise, chapter-wise, mock / full-length, half-yearly, full-yearly, and adaptive weak-area retest (§6.11).
  • FR-ASM-04 Test builder: fixed question list or blueprint (pick N of M from a pool per chapter/difficulty), section definitions, per-section timing, marking scheme, negative marking, attempts allowed, availability window, pause/resume policy.
  • FR-ASM-05 Randomisation: shuffle question order and option order per attempt; per-student question set from pools; anti-collusion seed per attempt.
  • FR-ASM-06 Test-taking runtime (web + mobile): countdown timer, autosave every N seconds, resume after crash/network loss, submit-on-timeout, question palette (answered / marked-for-review / unseen), section lock.
  • FR-ASM-07 Subjective answer input: rich text, LaTeX/equation, and image upload of handwritten answer (multi-page).
  • FR-ASM-08 Auto-grading for MCQ/numerical on submit. Manual grading for subjective: teacher queue, per-criterion rubric, partial marks, inline annotation, optional second-review/moderation, publish results.
  • FR-ASM-09 Result object: raw & percentage score, section scores, percentile, rank (cohort-scoped), accuracy, attempted/correct/incorrect/skipped, time per question, time vs cohort.
  • FR-ASM-10 Topic-wise & chapter-wise strength/weakness heatmap; comparison vs previous attempts; full solution review mode.
  • FR-ASM-11 Basic anti-cheating on MCQ: response-time anomaly detection, impossible-speed flags, duplicate-attempt prevention.
  • FR-ASM-12 P1.1 Institute-scoped leaderboards (toggleable), scheduled test series calendars.

6.11 AI Analysis & Adaptive Retests

  • FR-AI-01 After every graded test, a deterministic layer computes per-topic mastery from accuracy, difficulty, time, and trend across attempts, and classifies each topic as strong / borderline / weak.
  • FR-AI-02 An LLM generates a student-facing narrative: what went well, top 3 weak concepts, likely misconceptions, and a prioritised study plan with deep links to the exact lessons/PDFs for those topics.
  • FR-AI-03 Adaptive weak-area retest: on demand or auto-scheduled, the engine builds a new test drawn from the student’s weak topics using the blueprint sampler; difficulty adjusts based on the last attempt.
  • FR-AI-04 Progress view shows weak-topic list shrinking over time; “next best action” on the dashboard.
  • FR-AI-05 Optional diagnostic test per subject at onboarding to seed the initial mastery baseline.
  • FR-AI-06 All AI output is advisory, logged, and regenerable; prompts & model version stored with each analysis for reproducibility. No student PII beyond first name sent to the model unless configured otherwise.
Acceptance — Adaptive loop Given a completed chapter test where topics A and C are classified weak, when the student opens “Practice weak areas”, then a new test is generated containing only A/C-tagged questions not seen in the last attempt, and on completion the analysis shows updated mastery for A and C and an updated study plan.

6.12 Proctoring (subjective tests only)

  • FR-PRO-01 Proctoring is enabled only for subjective test types by default; a per-test flag can enable it for any test.
  • FR-PRO-02 Pre-test: identity selfie capture + stored reference photo match prompt, camera/mic permission, environment/system check, consent acknowledgement (student + Parent consent on file for minors).
  • FR-PRO-03 During test — web: enforced full-screen, tab-switch / window-blur detection, copy-paste & right-click block, periodic webcam snapshots (configurable interval), optional continuous webcam recording, disconnect handling with grace period.
  • FR-PRO-04 During test — mobile: app-backgrounding / app-switch detection with forced return, screenshot & screen-record block, no split-screen / picture-in-picture, incoming-call interruption logging, periodic front-camera snapshots.
  • FR-PRO-05 AI flags (in-house heuristics for MVP, optional vendor SDK): no face, multiple faces, face-not-matching-reference, phone/object detected, prolonged absence, background voices.
  • FR-PRO-06 Events & media stream to a Proctor Review dashboard (web, Teacher/Ops): per-attempt timeline, snapshot gallery, recording playback, severity score, decision = ACCEPT / FLAG / INVALIDATE + allow retake, reviewer notes.
  • FR-PRO-07 Proctoring media stored encrypted with a defined retention window (default 90 days) then auto-purged; access is role-limited and audited.

6.13 Payments & Billing (Razorpay)

  • FR-PAY-01 Catalogue of plans: per-subject, per-class bundle, full-year package, multi-year; one-time and subscription (monthly/annual) both supported; Institute-negotiated price overrides.
  • FR-PAY-02 Checkout: server computes final price (base − coupon + tax); creates Razorpay Order / Subscription; client uses Razorpay Checkout.
  • FR-PAY-03 Webhooks (signed, idempotent): payment.captured, payment.failed, order.paid, subscription.*, refund.processed, transfer.*, settlement.*.
  • FR-PAY-04 On successful capture: activate student access, record acquisition/attribution, accrue Institute commission, trigger invoice + confirmation email, count toward Institute commitment.
  • FR-PAY-05 Refunds: full/partial, reason codes, Ops approval workflow, GST credit note, access revocation policy, commission clawback from the Institute ledger.
  • FR-PAY-06 GST-compliant invoices: sequential numbering, company + customer details, HSN/SAC, tax breakup, downloadable PDF; stored in object storage.
  • FR-PAY-07 Failed-payment dunning: retry schedule + Brevo emails; subscription grace period & auto-suspend.
  • FR-PAY-08 Payment & reconciliation report: gross, discount, tax, net, fees, refunds, commission, platform revenue — per day / Institute / plan.

6.14 Commission Split & Settlement (Razorpay Route)

  • FR-COM-01 Each Institute maps to a Razorpay Linked Account; settlement is blocked until its KYC is active.
  • FR-COM-02 At payment time the engine reads the Institute’s ACTIVE contract and computes commission (percentage-of-net or fixed-per-student, honouring slabs).
  • FR-COM-03 Settlement mode per contract:
    • PER_TRANSACTION — create a Route transfer on the payment (immediate or on-hold).
    • WEEKLY / MONTHLY — accrue in the ledger, then a scheduled job creates a consolidated transfer/payout for the period.
  • FR-COM-04 Commission basis default = net of coupon; refunds create negative ledger entries and reduce the next settlement (or raise a recovery task if the balance is negative).
  • FR-COM-05 Per-Institute settlement statement (PDF/CSV): opening balance, accruals, adjustments, transfers, TDS note, closing balance; visible on the Institute dashboard.
  • FR-COM-06 Payout release requires Super Admin approval for consolidated cycles; all transfers reconciled against Razorpay transfer.* / settlement.* webhooks.
  • FR-COM-07 Dispute flag on a ledger line freezes that amount pending Ops resolution.

REST, base path /api/v1. JSON only. Auth via Authorization: Bearer <jwt> unless noted public. List endpoints support ?page, ?limit, ?sort, ?q and resource-specific filters. This is an indicative surface — roughly the average level of detail expected — not the exhaustive contract; the final OpenAPI spec is a build deliverable.

11. Security, Privacy & Compliance

  • Minors: most students are under 18. Signup for a minor is not complete until a linked Parent grants consent (account use, data processing, and — separately — proctoring & recording). Consent is versioned and logged (who, what version, timestamp, IP).
  • Proctoring media: webcam snapshots/recordings and identity selfies are sensitive. Stored encrypted at rest, access limited to Teacher/Ops with audit, default retention 90 days then auto-purge, and excluded from general exports.
  • Data-subject rights: endpoints/process for data export and deletion (right to erasure), with legal-hold overrides for financial records (retained per statutory requirement, typically 8 years for invoices/tax).
  • PII minimisation to AI: only first name + performance data sent to the LLM by default; configurable; prompts logged.
  • Access control: server-side RBAC on every route; tenant scoping guard; impersonation restricted & fully audited; 2FA mandatory for staff.
  • Secrets & keys: managed secret store, rotation policy, no secrets in code or client bundles; separate keys per environment.
  • Transport & storage: TLS in transit; encryption at rest for DB, object storage, and backups; signed, short-expiry URLs for all protected media.
  • Abuse protection: rate limiting, captcha on public forms, bot protection on auth, anomaly detection on test attempts and login.
  • Legal pages: Terms, Privacy Policy, Refund & Cancellation Policy, and a Proctoring & Consent notice published on the website and surfaced in-app at the point of consent.
  • Audit: immutable audit log for auth, role changes, impersonation, content publish, financial actions, contract state, and proctoring decisions.

12. Infrastructure & DevOps

12.1 Hosting recommendation

Recommended: AWS. ECS Fargate (API + workers) behind an Application Load Balancer, S3 for assets, CloudFront optional for the web app, MongoDB Atlas (peered), ElastiCache or Atlas-adjacent Redis, Route 53 DNS, ACM TLS, WAF on the ALB, Secrets Manager, CloudWatch + Sentry.

Lower-ops alternative: DigitalOcean. App Platform for API/web/workers, Spaces for assets, DO Managed MongoDB + Managed Redis, DO load balancer. Simpler and cheaper to operate for a small team; fewer knobs for fine-grained scaling.

Assumption Final choice pending client confirmation. Architecture and IaC are written to keep either option open; nothing in the application layer is provider-locked (S3-compatible storage API, standard Mongo/Redis).

12.2 Delivery pipeline

  • Mono-repo (pnpm workspaces): apps/api, apps/web, apps/website, apps/mobile, packages/common (shared types, validation, enums).
  • GitHub Actions: lint → type-check → unit → build → e2e (on PR) → deploy to staging on merge → manual promote to production.
  • Mobile: EAS build + submit; OTA updates for JS-only changes; staged rollout & forced-update gate.
  • Database migrations versioned & run in the pipeline; seed scripts for taxonomy and demo data.
  • Infra via Terraform; separate state per environment; least-privilege IAM.
  • Runbooks: restore-from-backup, webhook replay, key rotation, incident response.

  • Local (Docker Compose), Staging (sandbox integrations, open to client UAT), Production (isolated, monitored).
